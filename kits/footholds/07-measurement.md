# Footholds — Measurement

**Target: 1,000 consumer signups**, using the policy's no-product-account equivalent: **distinct first usable habit/focus sessions**. Do not claim these are verified individual accounts across devices. Claude sign-ins belong to the platform and must not be invented as Footholds registrations. Deduplicate refreshes conservatively and exclude your own tests.

Activation beside it: **a real user completes and records one ordinary tiny action**, with later independent sessions reported separately. A timer run isn't proof the action happened; use an optional user report without asking what private task it was. A demo Plus unlock, level, theme or missed-day pass isn't revenue or a completed habit.

## Day 0

Record actual usable sessions, task starts, real reported completions, return sessions and platform-access failures from appropriate owner records. Public level-one and greeting are not customer data. Capture current [course profile](https://shipped.money/p/footholds) rank, saved metric and timestamp; unknown isn't zero. The roster's generic developer-tool metadata is stale relative to the actual habit/focus artifact.

Check what analytics the hosted platform legitimately exposes before adding anything. You cannot assume control of the wrapper or claim [Clarity](https://clarity.microsoft.com/) measures actions inside it. If proper aggregate collection isn't available, use a small consented test log with no habit text or identity in public reports. Don't inject tracking or copy platform credentials to close a measurement gap.

Proposed content-free counts only if implementable: `usable_session_started`, `tiny_task_selected`, `timer_started`, `timer_completed`, `action_reported_done`, `return_session`, `feature_unavailable`. Keep actual chat responses, habit history and disability/health information out of analytics. Test persistence and reset on synthetic data before claiming cross-device continuity.

## Forecast from the actual schedule

- 30 invitations × assumed 50% try × 60% usable start = **nine sessions**; if half complete a real action, about four to five activations.
- Four posts × 200–600 impressions × 2% visit × 40% usable session ≈ **6–19 sessions**.
- One optional launch × 0–100 visits × 40% usable session = **0–40 sessions**.
- Three optional referral requests add zero guaranteed sessions; report actual results.

Total **15–68 first sessions before overlap**, below 1,000 and lower after deduplication. At an assumed 40% qualified-visitor-to-session rate, 1,000 needs 2,500 qualified visits. This calendar doesn't establish that reach, or that authentication-dependent features work for all of it. These are planning guesses, not habit efficacy or channel benchmarks.
