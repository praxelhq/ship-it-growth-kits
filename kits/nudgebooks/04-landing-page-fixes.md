# NudgeBooks — Entry-page fixes

Read [root/login](https://www.nudgebooks.in/) and the observed Create an account destination on 29 October 2026. Actual current headline/CTA: **“Sign in.”** Secondary **“Create an account”** opens **“Create your account”** at `/signup`. Metadata promises collecting documents without chasing; authenticated collection/messaging, pricing and persistence were not tested. No public software price was established.

## 1. Give a new practice a reason before the password

Current root opens a sign-in gate with no visible worked example.

Replacement supporting copy: **“For practices collecting recurring client documents. Inspect the current workflow before using real client data.”** Add a no-account fictional example only after it exists and reflects actual supported functions.

Keep the existing Sign in/Create account routes clear. Do not market a demo link that has not been built.

## 2. Define the actual collection route

Current metadata says without chasing but the public entry cannot establish how documents arrive or reminders happen.

Replacement description structure: **“Request method. Receipt/status method. Follow-up method. What requires your review.”** Populate with verified current behavior, not generic automation claims.

If a step is manual, say so. Do not invent WhatsApp integrations, automatic email reading, OCR or a client-upload portal.

## 3. State price and allowance before registration

Current entry publishes neither.

Replacement offer block: **“Review the current allowance and any price before creating your practice workspace.”** Fill actual terms from the configured release. No invented free-forever plan, trial duration, billing interval or tax treatment.

If account creation is only a private pilot, state who can join and how approval works rather than implying open onboarding.

## 4. Show privacy/access before client documents

Current login page does not establish client-document handling.

Replacement pre-use note: **“Use only client information your practice is authorized to process here. Review storage, access, retention and deletion before uploading or connecting a communication account.”**

Publish the real policy/support route. Test owner/staff/client views, direct links and revoked access with wholly fictional materials before actual records.

## 5. Separate received from requested

The intended wedge needs a reliable outstanding list; it is not an observed shipped feature set.

Once verified, use: **“Mark received only when the intended item actually arrived and was checked. A sent request is not receipt.”**

Test duplicate/wrong-period files, status edits and missing items. Do not mark a cycle complete because a reminder sent or somebody opened a link.

## 6. Verify a whole return cycle

Test fresh signup, supported request/status flow, return after sign-out, edit, deletion and any actual messaging permission. Use a synthetic client, then let an authorized owner choose a limited actual-data trial only after reviewing controls.

No real client files or inbox connection should be required for a sales demonstration. If a route fails, record the precise reproduction and repair before promotion. A login redirect is not a down site; a working signup form is not proof the collection workflow works.
