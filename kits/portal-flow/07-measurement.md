# PortalFlow — Measurement

**Target: 10 real business customers in 30 days.** Each studio must satisfy [all four tests](../../TARGET-POLICY.md): genuine operation; its own actual permitted work/data onboarded; independent use in the last seven days; privately known owner name/phone. Store identifiers outside the public repo. Fictional sample workspaces and discovery replies do not qualify.

Activation has separately reported stages: owner review setup with an actual permitted deliverable, and verified shared review where the intended recipient can inspect/act on the exact version and the studio receives the result. Report local-only versus shared activation explicitly. Do not imply actual client delivery if only a preview worked.

No private account records were accessed; release mode, active studios, saved projects and actual client deliveries are unknown.

| Baseline | Source / boundary |
| --- | --- |
| Verified current mode/access/offer | Owner-confirmed release and actual tests, reconciling demo metadata with rendered sign-in. |
| Real studios / latest independent use | Workspace records plus private permitted owner register, excluding seeded demos. |
| Owned deliverables and reviewed versions | Actual studio-owned data, not fictional default jobs. |
| Real recipient access/decisions received | Verified statuses and controlled test/owner feedback, not preview clicks. |
| Save/access/version/deletion failures | Synthetic reproductions and private issue categories. |
| Price/payment and course baseline | Actual configured offer if any, [profile](https://shipped.money/p/portal-flow), timestamp/period. |

Check existing [Clarity](https://clarity.microsoft.com/) before adding another tag. Exclude client art, private briefs/comments, client contacts, account fields, approval identities and access-bearing links from replay. Minimal events: ownprojectcreated, versionreviewed, localpreviewopened, recipientaccessverified, decisionreceived, laterindependentuse only where actually supported. Local preview events never become client-delivery events.

| Checkpoint | Decision |
| --- | --- |
| Day 7 | Eight approaches scheduled. If mode/persistence/invitation behavior cannot be established, keep sample discovery and fix the release contract. |
| Day 14 | 20 approaches. Compare owned setups with actual shared outcomes; fictional demo interest does not count. |
| Day 21 | 28 approaches. Inspect independent use and version/access failures, retaining truthful local/shared labels. |
| Day 28 | 40 approaches. Audit all four tests and count operating studios, not clients/projects. |
| Day 30 | Actual qualifying businesses against ten, both activation stages, independent return, actual offer, hours and gap. |

Base guesses: 40 × 50% × 70% × 70% = 9.8 businesses; at 25% conversation, 4.9. Three posts/two intros are upside only. These assume real supported own-work setup; release/privacy gates may leave zero qualifying customers. Replace assumptions after eight approaches and again after 20. A successful sample or assisted preview cannot be used as actual-business-data independent use.

A client approval is not automatically a legal signature, payment or completed engagement. A studio with useful local-only records may count only if all business tests hold, and must still be disclosed as local-only rather than a working shared portal. Publish real permitted aggregate observations and limitations; no invented studio wins, delivery counts or testimonials.
