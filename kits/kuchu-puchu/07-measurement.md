# Kuchu Puchu — Measurement

**B2C target: 1,000 signups in 30 days.** For this paid Mac app use **unique verified installs with a first launch**, one per real user. Report **activated pairs** beside it: two distinct accepted users who successfully exchange a greeting. One pair can contribute two users and one pair activation, never two pairs.

No private dashboard or app telemetry was accessed. Baselines are unknown until recorded; do not infer installs from download requests.

| Day 0 metric | Source |
| --- | --- |
| Real purchases, delivered files, refunds | Dodo records, excluding test transactions |
| First launches and verified sign-ins | Privacy-consistent application records; not update checks |
| Accepted pairs and first successful greeting | Aggregate delivery/receipt status |
| Week-one pairs returning voluntarily | Aggregate existing pair activity, no message text |
| Website traffic and sources | Existing opt-in Clarity, already described in the privacy notice |
| Latest course metric/rank/time | [Profile](https://shipped.money/p/kuchu-puchu) |

The [privacy notice](https://kuchupuchu.me/privacy.html) says Clarity is website-only and opt-in, not installed in the Mac app. Don't add a duplicate script or imply website replays measure app use. Keep emails, codes, photos, chats and purchase details out of recordings. Any new app telemetry must match the actual notice and user choices.

Track aggregate stages: purchase verified → file delivered → first launch → account verified → request accepted → greeting played. Separate incompatible-device questions from actual bugs. A quiet recipient choosing Work mode is exercising a feature, not necessarily churning.

| Checkpoint | Question | Action |
| --- | --- | --- |
| Day 7 | Can five willing pairs install and exchange a greeting? | Repair delivery/trust/pairing before wider promotion. |
| Day 14 | Where does receipt-to-first-pair lose people? | Clarify requirements or fix the blocked supported-device step. |
| Day 21 | Do pairs return without you prompting them? | No return: ask about occasion, control and interruption; don't add more features blindly. |
| Day 30 | First launches against 1,000, activated/repeat pairs beside it | State actual paid-beta ceiling and target gap honestly. |

The scheduled tests plausibly yield dozens rather than 1,000 installs. At 10% qualified visitor-to-paid-first-launch, 1,000 requires 10,000 qualified visits. If only half of installers connect a willing second user, paired activation will be much lower. Replace both assumptions with observed rates on Day 14.

Never count an update download as a new user, a pending request as an accepted pair, or a creator-code distribution as a paid sale. Course 24-hour traffic readings are not cumulative installs. The durable signal is a pair choosing to use the app again with recipient controls intact.
